## 1. Scope and method

The audit covered every tracked file in the repository (143). The baseline was green before review started: `pnpm build`, type-check, biome lint, `verify-fixtures`, `verify-palettes`, `pnpm test` (55 tooling, 338 package and 24 demo Playwright tests, 1 live test skipped) and `pnpm audit` (no known vulnerabilities). Only defects those checks do **not** catch are reported.

Area reviewers (reader, inspect, appearance, palettes, XIVAPI transport, XIVAPI resolver, demo, release, docs) each applied several lenses (correctness, security, contract, tests, docs drift, data hygiene, sweep) and produced 150 candidates in 99 clusters. Each cluster then went to two or three independent verifiers (reproduce, intent, impact). They used scratch repros against the prebuilt `dist`, mutation tests on scratch copies of `src`, and read-only checks of upstream producer source and the live XIVAPI and npm registry. No tracked file was edited; §9 lists incidental side effects.

A producer-compatibility pass covered Brio, Ktisis and Anamnesis. A gap critic then ran 7 extra lenses, none skipped.

Result:
- 106 findings: 103 settled by the verifiers, plus 3 disputes that the maintainer ruled to be low findings (F040, F052, F098)
- 0 open disputes: all 8 were resolved (§7); 5 were recorded as info observations
- 2 refuted candidates
- 27 unverified info-level observations (22 from review, plus 5 from dispute rulings)

Severities in this report are the verifiers' consensus.

## 2. Executive summary

There is **no critical issue**: no code execution, off-device data leak, budget bypass or release-integrity defect was found.

**Counts:** 0 critical, **2 high**, **28 medium**, **76 low** (106 findings). In addition there are 2 refuted candidates and 27 unverified info observations. The 8 verifier disputes were all resolved in §7 (3 became low findings, 5 became info).

**70 of the 103 verifier-settled findings are test or documentation gaps.** Many are documented guards that could be deleted or loosened in a mutation run with the whole suite still passing. Several status documents, including the supported-version policy, lag the beta.2 and beta.3 publications.

**Both high findings are producer-semantics errors in appearance output on real exports.** F090 affects Brio exports; F096 affects Anamnesis and Ktisis exports.

**Findings that matter most:**

1. **F090 (high) and F096 (high), plus F097 (medium): appearance output on real exports.**
   - Since v0.7.2, Brio stores each eye's extended colour under the other eye's name. The "historical" eye-swap heuristic repairs only the exact on-grid case, so custom eye colours land on the wrong eye.
   - The lip swatch ignores the lip-colour enable bit (`Mouth & 0x80`) that all three producers use, so characters with lipstick switched off show one.
   - Anamnesis never writes `IsExtendedAppearanceValid`, so its extended colours are never live. As a result, the same character renders differently depending on which producer exported it.
2. **F051 (medium): one missing row fails the whole batch.** The live XIVAPI answers HTTP 404 for a whole `rows=` batch when any row is missing. One unknown Stain or Glasses ID therefore makes the entire lookup `unavailable`. The documented `notFound` and "missing row" states cannot occur against the real API, and the test doubles model behaviour the API does not have.
3. **G008 (medium): reusing one resolver across requests breaks on Workers.** The docs advise exactly that reuse. In a stateless Cloudflare Worker, coalescing joins one request to another request's I/O. Per the workerd source and Cloudflare docs, the joiner is cancelled (error 1101) or left without anything to settle it, and queued jobs can be stranded. This is inferred, not executed.
4. **Security-gate evidence gaps (all medium):**
   - The CSP test accepts a widened policy (F064).
   - SEC-03 privacy tests ignore page-load and same-origin requests and never check console output (G004, G005).
   - The icon loader's bounds never run in CI (F061).
   - Several SEC-05 response and cache budgets can be removed without a test failing (F042, F043).
5. **F075 (medium): stale supported-version list.** `SECURITY.md` still accepts reports only for beta.1 and `main`. Per the npm registry, `next` now resolves to beta.3.

**Main themes:**
- A byte-identity review of pinned producer files cannot detect semantic differences that predate the pin (§5).
- Tests pin happy paths and over-limit rejections but rarely pin the guard itself.
- Test doubles encode XIVAPI and runtime behaviour that was never checked against reality.
- Demo state, focus and live-region handling is fragile across re-renders.
- Documentation drifted after the release.

## 4. Detailed findings: behaviour defects

This section covers defects in shipped behaviour of the library, tooling and demo, most severe first. §5 holds the compatibility findings that are mainly about documentation or provenance. §6 holds the test-coverage and documentation findings.

Each entry gives a location, the problem, a failure case, evidence, a fix and verification notes. Verification notes use these terms:

### 4.1 High

#### F090 · High · Brio v0.7.2+ eye extended colours are crossed; only the exact on-grid crossing is repaired
- **Location:** `packages/chara/src/appearance/resolve.ts:38-39` (fixed name pairing), `:96-132` (`pairEyes`).
- **Problem:**
  - The resolver pairs eye fields by name: `leftEye` reads `LEyeColor` + `LeftEyeColor`, and `rightEye` reads `REyeColor` + `RightEyeColor`.
  - Brio's 7.5 update (commit `5bec2d07`, 2026-04-30, first released in v0.7.2) relabelled the shader block, putting `RightEyeColor` at 0x40 and `LeftEyeColor` at 0x50. Current Anamnesis uses the opposite assignment: Left at 0x40, Right at 0x50. Brio's exporter copies the fields by name.
  - Result: every Brio export from v0.7.2 to head stores each eye's extended colour under the other eye's name, relative to the index pairing the library uses.
  - `pairEyes` swaps them back only when all of these hold:
    - both eyes are live;
    - their indices differ;
    - each colour lies within ΔE 1 of the *other* eye's shader colour and not within ΔE 1 of its own.
  - The rule is documented as "historical" (`docs/api.md:124`), but unmodified current Brio output depends on it.
- **Failure:**
  - The real `fixtures/producer-exports/brio-default.chara` (LEyeColor 169, REyeColor 42) is repaired: it reports `HISTORICAL_EYE_PAIR_SWAP` and shows the correct colours. With `historicalEyeCorrection: false`, both eyes come back `offGrid` at ΔE 26.51 with swapped colours, and `issues` is still `[]`.
  - Custom colour (authored edit B): a custom red set with Brio's "Left Eye Color" picker, which writes the slot that drives `REyeColor`, triggers no correction. Both eyes are falsely reported `offGrid`, and their display colours are swapped (`leftEye #E61A1A`, `rightEye #87C0A3`).
  - Shared index (edit C): the custom colour is attached to the opposite eye.
  - A colour only 1.2 ΔE from the shader default is enough to defeat the ΔE ≤ 1 test.
- **Evidence:**
  - Brio source: `Brio/Game/Actor/Interop/BrioHuman.cs` at `3f6f8e17`, `b510c82f` and head `be80fadb` has Right at 0x40 and Left at 0x50. Tag v0.7.1.2 still had Left at 0x60 and Right at 0x70.
  - Anamnesis source: `ExtendedAppearanceMemory.cs` at `3d635757` has Left at 0x40. Commit `819d395f` swapped back after a one-day flip.
  - The Brio and Anamnesis fixtures of the same character have identical indices but exchanged vectors.
  - Brio's per-eye pickers (`ModelShaderEditor.cs`, `ModelShaderOverride.cs`) write the live params that `ExportAppearance` serialises, so cases B and C are reachable with shipped Brio.
  - Brio is in practice the only producer whose extended colours ever go live (see F097).
- **Fix:**
  - Document the crossing in `docs/compatibility.md`: it applies to v0.7.2+, and pre-7.5 Brio is expected to be uncrossed.
  - State that the "historical" correction also covers current Brio output. Keep the public identifiers (`historicalEyeCorrection`, `HISTORICAL_EYE_PAIR_SWAP`, `historicalEyePairSwap`) unchanged.
  - Pin `corrections` and per-eye `displayHex` for `brio-default` (see F092).
  - Optionally emit a diagnostic when an off-grid eye pairing cannot be confirmed. A one-sided crossed match, as in case B, is a usable signal.
  - Do **not** swap unconditionally on files that look like Brio output. That would break pre-7.5 exports and the documented "no producer routing" rule (`docs/api.md:124`). The `SkinGloss: null` shape signal has not been validated against a real pre-7.5 export.
- **Verification:**
  - Confirmed 3/3. Severity votes: R high, I high, M medium. The impact verifier noted that unmodified exports resolve correctly and that the error is a left/right mirror of otherwise correct colours.
  - Library behaviour was reproduced against `dist`. Upstream semantics come from source review. Cases B and C are authored edits of the real export, not fresh Brio exports.

#### F096 · High · Lip swatch is active even when the producer's lip-colour flag is off
- **Location:** `packages/chara/src/appearance/resolve.ts:170-177` (`active`), `:309-327` (inactive and `noLip` paths), `:313-314` (reason mapping).
- **Problem:**
  - `active` is computed only for `highlights` (EnableHighlights) and `facePaint` (`!== 0`). Every other slot, the lip included, gets `true`. The parsed `Mouth` byte (`field-spec.ts:29`) is never read by appearance code.
  - All three producers treat bit 0x80 of that byte as "lip colour enabled":
    - Anamnesis: `EnableLipColor => Mouth >= 128` in the manifest-pinned `ActorCustomizeMemory.cs`.
    - Ktisis: `(lipType & 0x80) != 0`, with the colour button disabled when the bit is off.
    - Brio: `LipColorEnabled => (LipStyle & mask) != 0`.

- **Failure:**

#### G008 · Medium · Documented resolver reuse coalesces across Cloudflare Worker requests
- **Location:**
  - `packages/chara/src/xivapi/client.ts:576-577`: a caller joins an existing in-flight job.
  - `:586-589`: the deadline timer is created only for a new job.

  - The `jose` library disabled its single-flight fetch on Workers for the same reason.

  - First reproduce the problem in the wrangler harness: send two concurrent requests to a module-scope resolver, then a third case where the first request aborts.

    - (a) document that Worker hosts must create the resolver per request and share only the data cache. They must pass a module-scope `createMemoryCache()` explicitly; otherwise `createDyeNameResolver` builds a new cache on every call. With `version: 'latest'` this costs one `/version` call per request.

  - A per-joiner deadline timer on its own fixes B's 1101 but not the pump or slot leak.
